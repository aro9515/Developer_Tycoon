# 12. Developer Tycoon 룰북

모바일 웹에서 개발 회사를 운영한다. 월초에 한 달의 의뢰를 살피고, 매주 직원별로 납품·유지보수·교육에 쓸 시간을 정한다. 이번 주에 벌 돈과 다음 달에 팀이 맡을 수 있는 일 사이에 선택이 생기도록 설계한다.

| 상태 | 읽는 방법 |
| --- | --- |
| 구현 | 현재 저장소의 플레이 가능한 MVP에 있는 동작 |
| 합의한 방향 | 대화에서 채택한 설계 방향 |
| 제안 | 플레이로 검증할 세부 규칙·이름·콘텐츠 후보 |
| 미결 | 밸런스나 플레이 방식에 영향이 있어 별도로 결정할 항목 |

이 룰북은 기존 [게임 루프](03_게임루프.md), [직원 시스템](04_직원시스템.md), [프로젝트 시스템](05_프로젝트시스템.md), [기술 부채](06_기술부채시스템.md)를 바탕으로 후속 논의를 정리한다. 각 표에서 별도 상태를 적지 않은 카탈로그 항목과 수치는 제안이다.

## 1. 달력·의뢰·정산

| 항목 | 현재 MVP | 룰북 방향 |
| --- | --- | --- |
| 의뢰 목록 | 주간 정산에서 목록을 교체 | **합의한 방향.** 게임 내 월초에 이전 달 미수락 의뢰를 새 목록으로 교체한다. 수락한 의뢰는 담당자 배정 여부와 관계없이 계약·진행 상태를 들고 다음 달로 간다. |
| 주간 배정 | 개발자별 프로젝트 배정과 재배정 | **합의한 방향.** 직원은 한 주에 납품·보수·교육 등 주 활동 하나를 맡는다. 긴급 재배정은 기존 활동을 중단하고 남은 시간에 새 활동을 시작한다. 중단 시점까지 쌓은 진척과 노하우는 보존한다. |
| 계약 납기·담당자 | 담당자가 없으면 진행과 납기 판정용 경과 틱이 함께 멈춤 | **합의한 방향.** 진행 중인 계약에 담당자를 최소 한 명 유지한다. 최소 인원만 남으면 진척이 느려진다. 마지막 담당자가 퇴사해 생긴 공백 중에도 납기는 흐르며, 기한까지 후임을 배정하지 못하면 실패로 처리한다. |
| 계약 수입·중도 취소 | 수락 시 착수금, 완료 시 판정에 따른 잔금 | **합의한 방향.** 계약을 중도 취소하면 잔금은 받지 않고 착수금을 전액 반환한다. 담당 직원이 취소 전 실제 작업으로 얻은 개인 노하우는 보존한다. |
| 동시 계약 한도 | 회사에 동시 프로젝트 슬롯 값이 있음 | **합의한 방향.** 회사 성장 단계에서 고용 가능 인원이 늘어날 때 동시 계약 한도도 함께 늘린다. 구체적인 단계별 한도는 밸런스 항목이다. |
| 급여·고정비 | 매주 급여·임대료·서버비 차감 | **합의한 방향.** 주간 정산. 연봉 협상에는 인상 후 주간 비용도 표시한다. |
| 부채 이자·Heat | 매주 회사 부채(DP)에 이자를 가산. Heat 임계치에 닿으면 복구비가 들고 DP도 줄어듦 | **합의한 방향.** 주간 이자는 기술부채에 가산한다. 장애 대응으로 현금을 쓰면 서비스가 복구되고 Heat가 내려간다. DP 상환은 원인 수정·리팩토링에서 처리한다. |
| 유지보수 | 테스트가 납품 전에 버그를 줄임. 납품 후 보수 배정은 미구현 | **합의한 방향.** 장애가 없어도 부채가 쌓인 프로젝트는 보수와 변경에 공수가 더 든다. 보수 요청은 의뢰 시장 갱신과 별도로 주 단위로 검토한다. |

**합의한 방향.** 게임 내 한 달은 4주다.

**제안하는 경계 처리.** 한 주가 끝나면 진행·납품과 그 주에 완료한 상환을 반영하고, 남은 DP에 주간 이자를 붙인 뒤 급여·고정비를 정산한다. 다음 주에 직원 상태를 갱신하고, 월초라면 미수락 의뢰 목록도 한 번 갱신한다. 이자는 기존 MVP의 주 3%와 정수 내림으로 먼저 시험한다. 예를 들어 DP 100에서 보수로 20을 줄였다면 남은 80에 이자 2가 붙어 82가 된다. 이자율과 반올림 방식은 밸런스 항목이다.

**배정 공백의 경계 사례.** 수락과 동시에 첫 담당자를 정하고, 마지막 담당자를 다른 업무로 옮길 때는 대체자를 같은 배정에서 지정하는 안을 우선 본다. 마지막 담당자의 퇴사 전에 후임을 배정할 수 있다면 인수인계한다. 후임 없이 퇴사했다면 재배정까지 작업이 멈추고, 기존 계약 기한까지 후임을 배정하지 못하면 실패로 처리한다.

현재 진행·정산 동작은 [Game.ts](../src/core/Game.ts), [project.ts](../src/core/project.ts), [시장 생성](../src/core/market.ts), [밸런스 상수](../src/data/balance.ts)에서 확인할 수 있다.

웹과 모바일은 의뢰 분류로 사용한다. **기술 노하우는 기반 기술과 그 위에서 익히는 전문 기술로 연결**하는 안을 제안한다. 의뢰에는 화면·서버·데이터·운영 중 필요한 영역의 기술을 따로 넣는다.

| 회계·정산 | 대사·마감 절차를 다루는 도구 개발 | 여러 고객에서 반복된 대사·보고 요구 |
| 서비스 운영 | 장애 복구, 배포 절차 개선 | 적용한 운영 개선과 재발 여부 |

일반 능력치는 기본 작업에, 기술 노하우는 구현·검증에, 업무 노하우는 요구 파악·유지보수에 각각 연결한다. 회사의 납품 이력과 고객 반복 요구는 제품 판단에 쓴다.

**합의한 방향.** 중간 합류자의 인수인계 기간을 잡고, 전임자의 노하우 일부를 후임에게 전달한다. 후임의 관련 능력치가 높을수록 전달분은 작다. 인수인계 이후 자기 작업에서 얻는 노하우는 후임의 참여 시점을 기준으로 초반에 느리게, 익숙해지면 더 빠르게 쌓인다.

**제안.** 전달 대상은 해당 계약의 업무 흐름·주요 코드 위치·장애 대응법처럼 프로젝트에 필요한 지식으로 잡는다. 전임자와 후임이 함께 참여한 기간에 후임이 부족한 부분을 채우고, 후임의 관련 능력치가 높을수록 혼자 파악할 몫이 크다고 본다. 이미 갖춘 지식은 더하지 않는다. 인수인계 기간에는 두 사람의 시간을 해당 계약에 배정하며, 전달량과 퇴사 시 회사에 남는 범위는 검증한다.

## 3. 기본 직위·상위 직위

기본 직위 네 개와 상위 직위 네 개를 둔다. 관련 실무로 직위 경험을 쌓으면 전직 후보가 열린다는 안이다. 전직 후에도 이전 직위 이력과 개인 노하우는 남긴다. 전직 기준 레벨, 전직 비용과 시점, 연봉 반영은 미결이다.

| 기본 직위 | 연결 능력치 | 직위 경험이 쌓이는 실무 |
| --- | --- | --- |
| 프론트엔드 개발자 | 프론트엔드 | 입력 폼·대시보드 구현, 화면 보수 |
| 백엔드 개발자 | 백엔드·데이터베이스 | API·업무 로직 개발, 주문·정산 수정 |
| 서버 엔지니어 | 서버·인프라 | 배포, 모니터링, 장애 복구 |
| 프로젝트 코디네이터 | 커뮤니케이션 | 의뢰 상담, 요구 정리, 고객 검수 지원 |

| 상위 직위 | 전직에 필요한 기본 직위 경험 | 배정 시 역할 |
| --- | --- | --- |
| 풀스택 개발자 | 프론트엔드 개발자 + 백엔드 개발자 | 작은 화면·API 작업을 함께 맡아 인수인계 공수를 줄인다. |

| 솔루션 컨설턴트 | 서버 엔지니어 + 프로젝트 코디네이터 | 수락 전에 기존 환경·이관 공수·운영 위험을 파악한다. |
| 개발 PM | 프로젝트 코디네이터 + 프론트엔드 개발자 또는 백엔드 개발자 | 진행 중인 계약의 납기·범위 재협상을 이끈다. |

**제안.** 직위는 해당 배정에서 어떤 결정을 맡길 수 있는지를 정한다. 기초 구현은 스탯과 기술 경험으로 평가한다. 《게임개발 스토리》에서 직원 경험과 직종이 새 제작 선택지를 여는 구조를 참고했다. [카이로소프트 공식 설명](https://kairosoft.net/game/appli/gamedev.html)

## 6. 납품 위험·기술 부채·유지보수

| 상황 | 플레이어 선택 | 결과 후보 |
| --- | --- | --- |
| 무리한 의뢰 | 받기 전에 조건을 보고 수락·보류 | 높은 착수금과 부족해질 수 있는 공수가 함께 보인다. |
| 범위 변경 | 추가 대금·기한을 받고 수락, 원계약 유지, 개발 PM에게 조율 배정 | **합의한 방향.** 변경 빈도는 고객 성향에 따라 달라진다. 예를 들어 요구를 자주 바꾸는 고객과 변경을 드물게 요청하는 고객의 발생률을 다르게 둔다. |
| 납기 압박 | 스피드 모드, 인력 재배정, 고객 조율 | 스피드는 진척을 높이는 대신 버그·부채를 늘린다. 기한 초과는 납품 평가에 반영한다. |
| 버그 리포트 | 직접 보수, 현금을 내고 외주 보수, 다음 주로 미룸 | 배정이 비어 있는 직원의 점검 시간이나 유지보수 중 문제를 발견할 수 있다. 직접 보수한 직원은 경험을 얻고, 원인까지 해결한 작업은 부채를 줄인다. |
| 평상시 보수·변경 | 부채가 있는 프로젝트에 내부 인력을 배정하거나 외주를 맡김 | **합의한 방향.** 장애가 없어도 부채가 쌓인 프로젝트는 같은 작업에 공수가 더 든다. 외주도 처리 기간이 들며 실무 경험은 작업자에게 쌓인다. |
| 장애 복구 | 복구비를 지불해 서비스 재개 | **합의한 방향.** 서비스가 돌아오고 Heat가 내려간다. 원인이 된 DP는 원인 수정 작업으로 상환한다. |
| 원인 수정·리팩토링 | 장애 원인이나 반복 보수를 만드는 코드를 개선 | **합의한 방향.** 해결한 원인에 해당하는 DP와 향후 반복 보수 공수를 줄인다. |
| 코드 리뷰 미니게임 | 위험한 변경을 합치거나 배포하기 직전에 선택적으로 리뷰 | **제안.** 신규 기술의 첫 실전 적용이나 큰 범위 변경처럼 위험 신호가 있는 시점에 기존 배정 안에서 연다. 잘하면 버그 또는 신규 부채를 줄인다. |

**첫 시험.** 부채가 쌓인 프로젝트의 보수와 변경에 필요한 공수를 늘린다. 개발자 세 명 중 한 명이 그 주에 기존 고객 보수를 맡으면, 새 의뢰와 교육에는 두 명을 배정할 수 있다. 보수 요청은 배정이 비어 있는 직원의 점검이나 유지보수 중 발견으로 생길 수 있다. 같은 원인의 버그는 한 요청에 합치고, 수정하려면 공수를 배정한다. 현 MVP의 DP는 회사 단위다. 프로젝트별 발생·상환 이력을 연결하는 방식과 추가 공수의 크기는 검증한다.

**리뷰 발생 시점 제안.** 처음 적용하는 기술이나 큰 변경이 테스트·배포로 넘어가기 직전에 알린다. 첫 시험은 프로젝트당 한 번 이내로 시작한다. 실패 시 기본 테스트를 이어가는 안을 검토한다. 리뷰 조작과 보상은 초기 수치를 정한 뒤 플레이로 검증한다.

## 7. 고객 조율·연구 포인트

개발 PM은 진행 중인 계약에서 **납기 연장** 또는 **일부 기능을 다음 납품으로 이동** 중 하나를 제안한다. 원래 조건으로 진행하는 선택도 둔다. 제안 화면에는 납기·작업 범위에 생길 변화, 고객이 내세운 제약, 연구 포인트 사용에 따른 확률 변화를 표시한다.

| 결과 | 계약 변화 | 예시 |
| --- | --- | --- |
| 성공 | 제안한 납기 또는 범위를 반영 | 한 주 연장 또는 월말 보고서를 후속 납품으로 이관 |
| 실패 | 현재 계약 유지 | 고객 거절로 예정된 일정과 범위 유지 |
| 대실패 | 사전에 표시한 불리한 조건 적용 | 납기 단축, 중간 검수 앞당김, 추가 검수 항목·범위 발생 |

**제안.** 커뮤니케이션, 고객 신뢰, 요청 규모를 기본 판정에 반영한다. 연구 포인트를 쓰면 협의 근거를 준비해 성공 확률을 높이고 대실패 확률을 줄인다. 같은 조건의 협상을 반복하는 대신 계약이나 고객 조건이 바뀌었을 때 다시 시도한다.

| 조율 준비 예시 | 회사 연구 포인트 | 성공 | 실패 | 대실패 |
| --- | ---: | ---: | ---: | ---: |
| 기본 제안 | 0 | 50% | 40% | 10% |
| 공수 산정·시제품·장애 기록 첨부 | 3 | 70% | 25% | 5% |

수치는 화면·밸런스 검증용이다. 회사 연구 포인트는 버그 원인을 확인한 보수, 신기술 파일럿 검증에서 획득하는 안을 우선 본다. 개인 기술 노하우는 이후 배정에 쓰이고, 회사 연구 포인트는 중요한 시도의 성공 가능성을 높이는 데 쓴다. 첫 사용처는 고객 조율이며, 다른 사용처와 획득량은 미결이다. 《게임개발 스토리》 팬 가이드에는 개발·디버깅으로 얻은 연구 데이터와, 더 많은 데이터를 써서 직원의 작업 제안 성공률을 높이는 방식이 설명돼 있다. [수록된 게임 튜토리얼](https://kairo.waterbeetles.dev/en/game-dev-story/guide) · [연구 데이터 팬 위키](https://kairosoft.wiki.gg/wiki/Game_Dev_Story#Research_Data)

## 8. 직원 기대치·연봉 협상·아이템

| 직원 기대 | 초기 알림 | 대응 | 방치 시 흐름 |
| --- | --- | --- | --- |
| 연봉 | 희망 연봉과 현재 역할에 대한 불만을 말함 | 희망액 수용, 인상 역제안, 현 급여 유지. 인상 후 주간 비용을 표시한다. | 지속 시 면담, 대응 기회 뒤 퇴사 의사 |
| 워라밸 | 최근 연속 긴급 대응·스피드 배정 등 원인을 말함 | 다음 주 긴급 대응을 넘기거나, 업무량·스피드 배정을 줄인다. | 실제 과로가 줄었는지 평가하고, 지속 시 면담과 퇴사 의사 |

같은 불만은 직원별 원인별 요청 한 건으로 유지한다. 첫 경고, 면담 단계, 퇴사 의사처럼 상태가 바뀔 때 눈에 띄게 알린다. **합의한 방향.** 정기 연봉협상은 직원별 입사 1년이 지난 시점부터 입사일 기준으로 매년 진행한다. 급여 불만은 배정 화면에 먼저 표시한다. 정기 협상 전 임시 협상 허용 여부와 경고·면담·퇴사까지의 간격은 밸런스 항목이다.

회사 현금으로 구매하는 **복지·교육 상점**을 둔다. 직원 상세에서 효과와 사용 조건을 확인한다. **제안.** 식사 쿠폰과 기초 교재는 상시 판매하고, 기술별 실습 수강권은 월초에 소량 갱신한다. 쿠폰은 단기 스트레스, 교재는 작은 성장, 수강권은 해당 주의 교육 결과를 보강한다. 같은 주 반복 사용에 따른 효과는 첫 시험에서 제한한다.

| 아이템 예시 | 대상과 효과 | 사용 판단 |
| --- | --- | --- |
| 식사 쿠폰 | 긴급 납품 후 단기 스트레스·불만 완화 | 지속 과로 개선은 이후 배정으로, 연봉 차이는 협상으로 다룬다. |
| 고객 인터뷰 교재 | 커뮤니케이션 소폭 상승 | 새로운 고객 상담을 맡길 직원에게 사용 |
| C# 실습 수강권 | 해당 주 교육을 완료하면 C# 기초 노하우 추가 | 학습자를 배정할 주가 있을 때 사용 |

구매가·재고·사용 횟수와 성장량은 미결이다. 《게임개발 스토리》의 판매 채널과 아이템 사용은 구매 방식의 참고 사례다. [게임 튜토리얼 수록 가이드](https://kairo.waterbeetles.dev/en/game-dev-story/guide)

## 9. 신기술 도입·자사 솔루션

| 도입 방식 | 시작 조건·비용 | 위험과 이점 | 검토 순서 |
| --- | --- | --- | --- |
| 사내 파일럿 | 관련 업무 납품 경험을 바탕으로 한 사람을 교육·시제품에 배정 | 착수금이 늦어지거나 월초 교체 전에 의뢰를 놓친다. 검증 후 알맞은 의뢰에서 첫 실전에 적용하고 테스트 공수를 확인한다. | 먼저 시험 |
| 고객 프로젝트 내 부분 도입 | 고객이 기술 선택을 허용하고 팀에 업무 경험이 있는 의뢰에서 기능 하나를 시험 | 수주와 함께 시작할 수 있다. 혼용·통합 공수와 부채 위험이 생기며, 검증한 기능은 다음 의뢰에서 재사용할 수 있다. | 후속 |

**합의한 방향.** 파일럿은 기술과 관련된 일반 능력치를 갖춘 직원을 배정한다. **제안.** Spring Boot는 백엔드 능력치를 보고 Java 경험을 기초 준비도로 참고한다. Docker는 서버·인프라 능력치를 우선 본다. 첫 실전 적용의 추가 테스트 공수와 위험은 밸런스 항목이다.

기존 서비스는 고객의 기존 스택과 담당 경험을 유지할 이유가 있다. 예를 들어 C# 파일럿에 성공해도 기존 Vue 관리자 화면의 보수에는 Vue 경험이 필요하며, 시제품 검증만으로 기존 부채가 상환되지는 않는다. 파일럿 결과는 다음에 적용할 수 있는 일과 남은 검증을 한 줄로 보여준다. 직원 파견으로 제작 선택지를 여는 방송국 게임을 참고했다. [TV Studio Story 공식 설명](https://store.steampowered.com/app/2732020/TV_Studio_Story/)

자사 솔루션 후보는 **만들 수 있는 근거**와 **여러 고객이 필요로 한다는 근거**를 각각 보여준다. 여러 재고 고객이 월말 보고서를 반복 요청했고 팀이 관련 구현을 검증했다면 납품 결과에 공통 수요를 표시한다. 다음 주에 사람을 배정해 시제품을 만들고 판매할지 결정한다. **합의한 방향.** 출시 후에는 고객 유지보수 계약을 둘 수 있고, 지원에 공수나 비용이 든다. 판매·유지보수 수익과 지원 비용, 제품 후보를 여는 고객 수와 기술 검증 기준은 밸런스 항목이다. ## 10. 모바일 화면과 한 달 플레이 예시

| 화면 | 기본으로 보여줄 정보 | 상세를 여는 순간 |
| --- | --- | --- |
| 사무실 | 월·주, 현금, 직원별 이번 주 배정, 선택 프로젝트 진행률 | 직원을 고를 때 현재 배정, 적합한 이유, 옮기면 비는 업무 |
| 의뢰 | 기술 고정 여부, 기간·보상, 월말 만료 여부 | 수락 전에 요구 스탯, 고객 조건, 관련 납품 이력 |
| 직원 | 직위, 현재 업무, 주의할 불만 | 교육·전직·아이템 사용, 연봉·워라밸 대응을 고를 때 |
| 결과 | 주간 정산은 요약, 납품·첫 파일럿은 결과와 원인 | 잔금, 경험, 남은 버그·보수·제품화 기회를 확인할 때 |

사무실에서 팀이 움직이고 현재 작업 지표를 함께 읽는 원리를 가져온다. 시설 인접 효과와 동선 편집은 공간 배치 자체가 전략이 되는 경우의 후속 후보다. 월초 의뢰 교체는 Developer Tycoon의 설계 선택이다. [게임개발 스토리 공식 상세](https://kairosoft.net/game/appli/gamedev.html) · [Anime Studio Story 제작 화면](https://kairosoft.net/game/shared/image/gm73/img_04.png) · [Pocket Academy 3](https://store.steampowered.com/app/2191490/Pocket_Academy_3/) · [Hot Springs Story 2](https://store.steampowered.com/app/2089450/Hot_Springs_Story_2/)

1. 월초에 C# 적용이 가능한 재고 의뢰를 본다. 첫째 주에 수현이 기존 웹 의뢰를 납품하고, 지민은 C# 교육을 받는다. 재고 의뢰는 시장에 남고 착수금은 다음 주로 밀린다.
2. 다음 주에 재고 의뢰를 수락하고 지민을 배정한다. 수현은 이전 납품의 버그를 고쳐 부채를 줄인다. 원인 확인으로 연구 포인트를 얻는 예시다.
3. 고객이 보고 항목을 추가하려 하자 개발 PM에게 조율을 맡긴다. 포인트를 써서 일부 보고서를 후속 납품으로 넘길 가능성을 높인다. 성공하면 확보한 공수를 첫 C# 적용 검증에 쓴다.
4. 월말에 수락한 재고 프로젝트가 진행 중이면 다음 달에도 이어진다. 미수락 의뢰만 교체한다. 완료 후 여러 고객의 공통 보고 요구가 확인되면 자사 솔루션 후보를 검토한다.

## 11. 첫 적용 순서와 남은 결정

| 단계 | 먼저 확인할 플레이 | 미결 |
| --- | --- | --- |
| 달력·배정 | 담당자를 유지하면서 월초 의뢰에 맞춰 주간 배정을 바꾸는가 | 단계별 고용·계약 한도와 이자율 |
| 납품·보수·교육 | 납기를 앞당겨 얻은 여유와 이후 보수에 필요한 추가 공수가 배정 선택을 바꾸는가 | 프로젝트별 부채 기록, 추가 보수 공수·외주 기간, 초기 노하우 목록, 성장·인수인계·보수 보상 |
| 직위·사람 운영 | 전직·면담·아이템이 실제 배정 선택지를 늘리는가 | 전직 레벨·비용·연봉, 아이템 가격·재고, 불만 기간·퇴사 처리 |
| 조율·파일럿·제품 | 연구 포인트를 쓸 이유와 다음 활동의 기회비용이 읽히는가 | 조율 확률·비용, 첫 프로덕션 적용 위험, 제품화·출시 후 운영 |
| 추가 이벤트·화면 | 범위 변경, 버그 리포트, 리뷰가 핵심 배정을 보강하는가 | 리뷰 조작·빈도·보상, 그래픽 개선의 범위 |

**밸런스 검증.** 교육·전직, 불만 지속 기간, 상점 가격, 조율 확률과 연구 포인트, 신기술 위험과 제품 계약의 수치를 거친 초기값으로 둔다. 규모가 작은 회사와 성장한 회사를 여러 번 시뮬레이션해 주간 현금, 납기 지연률, 보수 적체, 교육·전직까지 걸리는 주, 이직 빈도를 비교한다. 실제 플레이에서는 교육이나 연구 포인트 사용이 언제나 같은 답으로 굳어지는지 확인한다.

**장기 방향.** 모바일 웹에서 플레이와 인터페이스를 다듬으며 달력·배정·정산·결과 기록을 화면과 소재 데이터에서 분리한다. 여러 작품에서 실제로 재사용되는 규칙이 확인되면 공통 코어를 추출하고, 반복되는 데이터 편집과 밸런스 검증을 제작 도구로 만든다. 특정 스택·고객 요구·코드 부채의 상세 규칙은 Developer Tycoon에 둔다. Godot과 Unity는 추후 제작상의 필요가 생기면 비교할 후보이며, 엔진과 전환 시점은 미결이다.
