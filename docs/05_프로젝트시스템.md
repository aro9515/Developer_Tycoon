# 05. 프로젝트 시스템

## 1. 설계 목표

프로젝트는 **돈의 원천**이자 **부채·성장·신뢰의 무대**.  
수주 선택이 “무엇을 희생할지”를 보여주는 카드 게임이 되게 한다.

---

## 2. 프로젝트 속성

| 속성 | 설명 |
|------|------|
| title / clientType | 이름, 고객 유형 |
| budget | 총 계약금 (착수금 + 잔금) |
| durationTicks | 기준 기간 |
| difficulty | 1~5 |
| requirements[] | 스킬/스택 요구량 |
| bugTolerance | 납품 시 허용 버그 |
| clientPersonality | 고객 성격 태그 |
| trendTags | 사용 스택의인기 연계 |
| maintenanceLoad | 완료 후 주간 공수 |
| reputationReq | 수주에 필요한 최소 신뢰 |

### 고객 성격 (원본 “고객 성격” 구체화)

| 성격 | 수주 시 | 진행 중 | 완료 시 |
|------|---------|---------|---------|
| 꼼꼼함 | 예산 평범 | 요구변경↓, 버그허용↓ | 품질 보너스 |
| 구두쇠 | 예산 ↓ | 잔금 깎기 이벤트 | 신뢰만 ↑ |
| 변덕 | 예산 ↑ | 요구변경 빈번 | 성공 시 신뢰 대폭 |
| 침묵 | — | 피드백 없음(테스트 어려움) | 평범한 정산 |
| 기술이해 | — | 스택 선택 간섭 | 트렌드 보너스/패널티 |
| 급한불 | 기간 ↓ | 스피드 압박 | 실패 시 신뢰 −− |

## 3. 프로젝트 라이프사이클

상세 상태: `03_게임루프.md` 참고.

### 3.1 수주 시장
- 슬롯 3~6개 동시 노출
- 매주 리프레시 + 긴급 의뢰(높은 보상/높은 리스크)
- 동시 진행 가능 수 = `projectSlots` (성장으로 해금)

### 3.2 개발 중 선택 (스피드 삼각관계)

```
        품질
        /  \
       /    \
    일정 —— 부채
```

| 모드 | 진행 | 버그 | TechDebt | BurnDebt |
|------|------|------|----------|----------|
| 정상 | 100% | 기준 | 소량 | 0 |
| 스피드 | 130% | + | +중 | 0 |
| 야근 | 160% | ++ | +소 | +중 |
| 완벽주의 | 70% | −− | − | +소(스트레스) |

## 4. 결과 판정

원본: 대성공 / 성공 / 보통 / 실패

```
score = qualityScore
      - bugPenalty
      - overduePenalty
      + clientBonus
      - debtPenalty(atDelivery)

대성공: score ≥ 90
성공:   70~89
보통:   50~69
실패:   < 50 또는 기간 초과 + 버그허용 초과
```

| 결과 | 잔금 | 신뢰 | XP | 기타 |
|------|------|------|-----|------|
| 대성공 | 120% | ++ | ++ | 특수 의뢰 해금 확률 |
| 성공 | 100% | + | + | — |
| 보통 | 80% | 0 | + | 유지보수 부하 + |
| 실패 | 0~30% | −− | 소 | 부채 일부 잔존, 랭킹↓ |

## 5. 독창 시스템 C — 레거시 앵커 (Legacy Anchor)

### 문제
타이쿤에서 “완료 = 끝”이면 중반이 시시해짐.

### 해결
완료 프로젝트는 **유지보수 앵커**로 남아 주간 공수를 먹는다.

| 상태 | 효과 |
|------|------|
| 정상 유지보수 | 주간 공수 소모, 신뢰 유지, 소액 MRR |
| 방치 | TechDebt +, 장애 확률 +, 신뢰 서서히 − |
| 리팩토링 스프린트 | 공수 집중 투입 → 부채↓, 유지보수 부하↓ |
| 폐기/이관 | 비용 지불 or 신뢰 − 로 슬롯 해방 |

**플레이**: 외주를 많이 받을수록 “과거가 발목을 잡음”.  
연구(자동 모니터링)로 앵커 부하를 깎는 것이 중반 목표.

## 6. 독창 시스템 D — 트렌드 메타 (Stack Trend)

### 개념
스택마다 **인기도(0~100)** 가 시간에 따라 변한다.

| 인기 | 효과 |
|------|------|
| 높음 | 해당 스택 수주 보상↑, 채용 희망자↑, 직원 사기↑ |
| 낮음 | 보상↓, “레거시” 낙인, 유지보수 인력 구하기 어려움 |

### 이벤트 연동
- “신규 프레임워크 등장” → 특정 스택 인기 급상승, 기존 ↓
- 회사가 구식 스택에 묶여 있으면 채용·수주에 패널티
- 반대로 구식 스택 장인 회사 빌드(레거시 수주 특화)도 가능

### 이력서 드리븐 갈등
직원이 `트렌드 추종` 특성이면 인기 스택 프로젝트 배치를 요구.  
거절 시 사기↓, 수락 시 학습 비용(일시적 진행↓) 발생.

## 7. 요구사항 카드 (프로젝트 내부)

프로젝트를 단일 게이지만으로 두지 않고, **요구 카드 N장**으로 분해 (원본 “요구사항 수”).

예:
- [FE] 반응형 UI
- [BE] 결제 API
- [DB] 스키마 설계
- [Infra] 배포 파이프라인

각 카드에 담당자 할당 → 카드 완료율 합 = 진행도.  
스피드 모드 시 카드가 “대충 완료” 상태가 되어 **부채 태그**가 붙음.
